# Stage 7: Split Crawler Database and Crawl Responsibilities

## Problem / Goal

Stage 7 makes the TypeScript crawler maintainable without changing the crawler output consumed by Engine jobs and Engine API readers. The crawler currently works, but most SQLite schema compatibility logic, migrations, store classes, repository-style methods, and helper functions live in one large module:

```text
engine/crawler/src/db.ts
```

That file currently owns all of these responsibilities at once:

```text
base crawler schema application
runtime compatibility migrations for instances/channels/videos
filesystem/database opening behavior
WAL pragma setup
instance queue/state/edge persistence
instance progress and error recording
channel persistence and progress recording
channel health and videos_count recording
video persistence and progress recording
video tags/comments/error recording
large row/type definitions for all crawler stores
shared delete/chunk helpers
```

The goal is to split that file into narrow database modules while preserving every current crawler command, DB shape, progress table behavior, retry/error recording behavior, and generated output consumed by Engine jobs.

Current crawler command boundary that must remain stable:

```text
cd engine/crawler && npm run build
cd engine/crawler && npm run crawl:instances
cd engine/crawler && npm run crawl:instances:health
cd engine/crawler && npm run crawl:channels
cd engine/crawler && npm run crawl:channels:health
cd engine/crawler && npm run crawl:channels:videos-count
cd engine/crawler && npm run crawl:videos
cd engine/crawler && npm run crawl:videos:tags
cd engine/crawler && npm run crawl:videos:comments
```

Current code paths found in the real codebase:

```text
engine/crawler/src/crawler.ts
  imports CrawlerStore from ./db.js
  owns PeerTube instance traversal and calls CrawlerStore for persistence.

engine/crawler/src/channels-worker.ts
  imports ChannelStore and channel row/progress types from ./db.js
  owns PeerTube channel traversal and calls ChannelStore for persistence.

engine/crawler/src/channels-videos-count-worker.ts
  imports ChannelStore from ./db.js
  owns channel videos_count update traversal.

engine/crawler/src/instances-health-cli.ts
  imports ChannelStore from ./db.js
  owns instance health check command behavior.

engine/crawler/src/videos-worker.ts
  imports VideoStore and video row/progress types from ./db.js
  owns PeerTube video traversal, tag updates, comment updates, and invalid/error recording.
```

Stage 7 should keep those worker/CLI behavior boundaries intact and first make the database layer readable. It should not rewrite crawler network traversal, pagination, command-line flags, PeerTube request behavior, or Engine jobs.

## Expected Behavior

After Stage 7:

- Existing Stage 0-6 tests still pass.
- `make test` remains green.
- Crawler command names and CLI flags remain unchanged.
- `engine/crawler/src/db.ts` remains import-compatible as a facade for existing imports:

```ts
import { CrawlerStore } from "./db.js";
import { ChannelStore, type ChannelProgressRow, type ChannelUpsertRow } from "./db.js";
import { VideoStore, type VideoChannelRow, type VideoProgressRow, type VideoTagRow, type VideoUpsertRow } from "./db.js";
```

- The crawler still writes the same SQLite tables, columns, indexes, primary keys, defaults, and row shapes defined by `engine/crawler/schema.sql` plus the current compatibility migrations in `db.ts`.
- Existing progress semantics remain unchanged:
  - `instance_crawl_progress.status` transitions remain current behavior.
  - `channel_crawl_progress.status`, `last_start`, `last_error`, `last_error_at`, and `updated_at` behavior remain current behavior.
  - `video_crawl_progress.status`, `last_start`, `last_error`, `last_error_at`, and `updated_at` behavior remain current behavior.
- Existing retry/error semantics remain unchanged:
  - instance errors update `instances.last_error`, `last_error_at`, and `last_error_source` with current source names;
  - channel errors update channel/instance error columns with current source names;
  - video invalid/error paths update `invalid_reason`, `invalid_at`, `last_error`, `last_error_at`, and `error_count` with current SQL behavior.
- Existing generated `dist/` behavior remains unchanged:
  - `dist/` is still generated by `npm run build`;
  - `dist/` remains ignored and not committed;
  - job documentation can continue to say crawler JS files are generated before updater/job execution.
- Engine jobs can continue to consume crawler output without manual migration or DB repair.

## Architecture

Stage 7 changes only crawler database module organization.

Current crawler architecture:

```text
engine/crawler/src/*-cli.ts
  -> parse command-line options
  -> call worker functions

engine/crawler/src/*-worker.ts and crawler.ts
  -> own PeerTube traversal/pagination/concurrency/retry orchestration
  -> call CrawlerStore / ChannelStore / VideoStore

engine/crawler/src/db.ts
  -> owns all DB connection, schema compatibility, stores, repository behavior, and row types
```

Target Stage 7 crawler database architecture:

```text
engine/crawler/src/db.ts
  -> compatibility facade only; re-exports current public classes and types

engine/crawler/src/db/connection.ts
  -> filesystem directory creation, optional reset behavior, SQLite open, WAL pragma

engine/crawler/src/db/schema.ts
  -> applyBaseSchema and current compatibility migrations for instances/channels/videos
  -> table/column existence helpers used only by crawler DB modules

engine/crawler/src/db/types.ts
  -> StoreOptions, ChannelStoreOptions, VideoStoreOptions
  -> current row/progress/status/upsert interfaces

engine/crawler/src/db/instances.ts
  -> CrawlerStore and instance queue/state/edge/progress persistence

engine/crawler/src/db/channels.ts
  -> ChannelStore and channel/instance health/videos_count/progress persistence

engine/crawler/src/db/videos.ts
  -> VideoStore and video/progress/tags/comments/invalid/error persistence

engine/crawler/src/db/utils.ts
  -> shared small DB helpers such as deleteInstancesInChunks when needed
```

Worker and CLI ownership remains unchanged in Stage 7:

```text
crawler.ts
channels-worker.ts
channels-videos-count-worker.ts
instances-health-cli.ts
videos-worker.ts
```

They may continue importing from `./db.js`, or they may be changed to import from `./db/instances.js`, `./db/channels.js`, and `./db/videos.js` only if doing so does not affect generated JS command behavior. The compatibility facade in `db.ts` is mandatory either way, because it preserves external import compatibility for any local scripts not covered by repository search.

### Responsibility boundaries preserved by Stage 7

Stage 7 owns:

```text
crawler DB module split
crawler DB repository tests
crawler build/test command documentation
crawler compatibility documentation
```

Stage 7 does not own:

```text
Engine API routes or recommendation behavior
Client backend behavior
frontend behavior
Python Engine runtime migrations from Stage 6
crawler schema redesign
historical schema_migrations framework
updater-worker orchestration split
PeerTube network traversal redesign
HTTP retry/backoff redesign
CLI flag redesign
npm workspace migration
FastAPI/framework migration
```

### Remaining ownership after Stage 7

After Stage 7, the following ownership remains intentional and is not a gap:

```text
CLI parsing remains in engine/crawler/src/*-cli.ts.
PeerTube traversal, pagination, concurrency, and HTTP retry usage remain in crawler.ts and *-worker.ts.
Crawler DB connection/schema/store behavior lives under engine/crawler/src/db/.
engine/crawler/src/db.ts remains a compatibility facade.
Engine jobs still consume the crawler DB output but do not own crawler DB writes.
```

Future stages:

```text
Stage 8: frontend page split; no crawler work.
Stage 9: updater/jobs/deployment split; may adjust how jobs invoke already-built crawler commands.
A later dedicated crawler network stage may split PeerTube API client/pagination helpers if needed.
```

#### 2.1 Instance store behavior

File:

```text

```

Scenarios:

```text

- constructor with collectGraph/expandBeyondWhitelist creates queue, edges, and crawl_state only according to current options.

- enqueueHost + claimNextHost returns due host and marks progress as processing.
- markDone clears instance error fields and marks progress done.
- markError sets last_error, last_error_at, last_error_source='instances', increments error_count, and marks progress error.
- insertEdge ignores self-edges and inserts non-self edges idempotently.
- recoverQueue resets processing progress to pending and re-enqueues allowed pending hosts.
```


```text
Compatibility migrations from db.ts change table/column shape.
```

Action:

```text
Move migration SQL text mechanically into db/schema.ts and keep table/column existence guards. Add tests that create rows through stores and inspect current columns/index-sensitive behavior. Do not edit schema.sql.
```



## Compatibility and Protocol Notes

Crawler behavior is PeerTube-specific because it consumes PeerTube public instance/channel/video endpoints and stores PeerTube metadata in the project crawler schema.

Stage 7 repository behavior is project-specific because `engine/crawler/schema.sql`, progress tables, and error fields are PeerTube Browser contracts consumed by Engine jobs.

No generic ActivityPub or federation protocol behavior is introduced in Stage 7.

No public HTTP API behavior is introduced in Stage 7.
